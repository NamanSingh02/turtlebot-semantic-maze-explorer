Assignment 1: Getting Started with ROS

Use ROS 2 Jazzy inside Docker on the Ubuntu 24.04 EC2 instance, with an Amazon DCV console desktop for Gazebo and RViz2. SSH access is already available. The laptop displays the desktop while EC2 runs the simulation.

These instructions are based on repository inspection and official documentation. They have not yet been executed on EC2. Complete each checkpoint before continuing.

1. Understand the components

ROS 2 allows robot programs to exchange data and commands. Gazebo simulates the robot, maze, sensors, and movement. RViz2 displays ROS data, including the map and robot position. Nav2 plans and controls navigation. Docker packages software dependencies, Compose starts the configured containers, and DCV streams the EC2 desktop.

A node is a running robot program. A topic is a named message stream. A pose is position and orientation. TF describes relationships between coordinate frames. A launch file starts related programs together.

2. Check the EC2 machine

Where: the existing SSH terminal.

cat /etc/os-release
uname -m
free -h
df -h /
nvidia-smi

Expect Ubuntu 24.04, x86_64, approximately 32 GiB RAM, and an NVIDIA T4. Keep at least 40 GB free for the desktop and builds; a 100 GB root EBS volume provides headroom. If necessary, expand the EBS volume and filesystem before building. Instance-store capacity is separate from the root filesystem.

3. Install the NVIDIA driver if necessary

Where: SSH terminal.

If nvidia-smi already works, keep the existing driver and skip installation. Otherwise run:

sudo apt update
sudo apt install -y ubuntu-drivers-common
sudo ubuntu-drivers install
sudo reboot

Reconnect after reboot and run nvidia-smi. Continue only when the GPU appears without a driver communication error.

4. Install the graphical desktop

Where: SSH terminal.

sudo apt update
sudo apt install -y ubuntu-desktop mesa-utils xauth x11-xserver-utils nvidia-xconfig

Choose gdm3 if asked for a display manager. Open its configuration:

sudo nano /etc/gdm3/custom.conf

Under [daemon], ensure this line exists and is uncommented:

WaylandEnable=false

Save with Ctrl+O, press Enter, then exit with Ctrl+X. Configure the NVIDIA display:

sudo nvidia-xconfig --preserve-busid --enable-all-gpus --allow-empty-initial-configuration --virtual=1920x1080
sudo systemctl set-default graphical.target
sudo reboot

This prepares an X11 desktop without a physical monitor. Reconnect over SSH after rebooting.

5. Install Amazon DCV

Where: SSH terminal.

mkdir -p ~/dcv-install
cd ~/dcv-install
wget https://d1uj6qtbmh3dt5.cloudfront.net/nice-dcv-ubuntu2404-x86_64.tgz
tar -xzf nice-dcv-ubuntu2404-x86_64.tgz
cd nice-dcv-*-ubuntu2404-x86_64
sudo apt install -y ./nice-dcv-server_*.deb ./nice-dcv-web-viewer_*.deb
sudo usermod -aG video dcv
sudo systemctl enable --now dcvserver
sudo passwd ubuntu

Set a password for desktop authentication. Password characters are not displayed while typing. Create a console session:

sudo dcv create-session --type=console --owner=ubuntu robotics
sudo dcv list-sessions

Expect a session named robotics. If extraction has produced multiple versioned directories, enter the directory from the current download explicitly rather than using the wildcard.

In the AWS console, give the EC2 IAM role this policy, replacing YOUR_REGION with the instance's region:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::dcv-license.YOUR_REGION/*"
    }
  ]
}

Add the permission to the existing role. If no role exists, create one trusted by EC2 and attach it through EC2 → Instance → Actions → Security → Modify IAM role. Ensure outbound HTTPS access to S3 for DCV licensing.

6. Connect to the desktop

Where: a new terminal on the laptop.

Replace the key path and public IP, then leave this SSH tunnel running:

ssh -i "/path/to/your-key.pem" -N -L 8443:localhost:8443 ubuntu@YOUR_EC2_PUBLIC_IP

Open https://localhost:8443 in the laptop browser. The initial DCV certificate is self-signed, so a certificate warning is expected for this connection through the private SSH tunnel. Log in as ubuntu using the password just set, select robotics if prompted, and log into the Ubuntu desktop if its login screen appears.

The tunnel does not require opening port 8443 publicly. Keep SSH access restricted to the appropriate source IP.

Open Terminal inside the remote desktop:

echo "$XDG_SESSION_TYPE"
echo "$DISPLAY"
glxinfo -B

Expect x11, a nonempty display, and an NVIDIA renderer. If the renderer is llvmpipe, investigate CPU rendering before expecting good simulation performance. Run subsequent graphical commands inside the DCV desktop terminal so they inherit its display environment.

7. Install Docker and Compose

Where: EC2 desktop terminal.

docker --version
docker compose version

If both work, skip installation. For a fresh installation run:

sudo apt update
sudo apt install -y ca-certificates curl git gnupg
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

sudo tee /etc/apt/sources.list.d/docker.sources > /dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: noble
Components: stable
Architectures: amd64
Signed-By: /etc/apt/keyrings/docker.asc
EOF

sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo usermod -aG docker "$USER"

Log out of the Ubuntu desktop and log back in to apply group membership. Open a new terminal:

docker run --rm hello-world
docker compose version

Expect the hello-world success message and a Compose version. Permission-denied errors can indicate that the group membership has not taken effect.

8. Enable container GPU access

Where: EC2 desktop terminal.

curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey | sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg

curl -fsSL https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list | sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' | sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list

sudo apt update
sudo apt install -y nvidia-container-toolkit
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker
docker run --rm --gpus all ubuntu:24.04 nvidia-smi

Expect the T4 inside the container. This confirms GPU access, not OpenGL rendering.

9. Download the course project

Where: EC2 desktop terminal.

mkdir -p ~/robotics
cd ~/robotics
git clone https://github.com/pantelis/turtlebot-maze.git
cd turtlebot-maze
ls
cat .env
git rev-parse HEAD

Use a clean course checkout for the initial assignment. Expect ROS_DISTRO=jazzy. Retain the commit identifier in experiment notes. Use turtlebot-maze consistently even where the README refers to the original upstream repository name.

10. Configure the simulation GPU and display

Where: EC2 desktop terminal, inside ~/robotics/turtlebot-maze.

For a fresh checkout, create the following override. If docker-compose.override.yml already exists, merge these settings instead of overwriting it.

cat > docker-compose.override.yml <<'EOF'
services:
  demo-world:
    environment:
      TURTLEBOT_MODEL: "3"
      NVIDIA_VISIBLE_DEVICES: all
      NVIDIA_DRIVER_CAPABILITIES: all
      __GLX_VENDOR_LIBRARY_NAME: nvidia
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [gpu]
EOF

Compose combines this override with docker-compose.yaml. Allow the container's root user to open desktop windows:

xhost +SI:localuser:root
echo "$DISPLAY"
echo "$XAUTHORITY"

If XAUTHORITY is empty, check the conventional file:

export XAUTHORITY="$HOME/.Xauthority"

test -f "$XAUTHORITY" && echo "Display authentication file found"
docker compose config --quiet

If the authentication file check fails, resolve the desktop authentication path before continuing. Do not create a directory named .Xauthority. Expect Compose validation to finish without errors.

11. Build the required image

Where: EC2 desktop terminal, project folder.

docker compose build demo-world

This downloads ROS, installs dependencies, and builds the robot and maze packages. The first build can take tens of minutes. Build only demo-world for this assignment to avoid unnecessary detector, SLAM, and database builds. Continue only after a successful build.

12. Check container rendering

docker compose run --rm --no-deps demo-world glxinfo -B

Expect an NVIDIA OpenGL renderer. Successful nvidia-smi output alone does not prove that graphical applications use the GPU.

13. Launch the maze

docker compose up demo-world

Leave the terminal running. Expect Gazebo, the maze, TurtleBot, sensor bridges, RViz2, and Nav2. Run only one world service at a time.

In Gazebo, verify that the maze appears, the robot is resting on the floor, and playback is active. Use the play button if paused. Select the robot in the scene list to locate it if necessary.

In RViz2, verify that the map, robot model, and laser points appear and broadly align with the map walls.

14. Verify ROS and sensor data

Where: a second EC2 desktop terminal.

cd ~/robotics/turtlebot-maze
docker compose exec demo-world bash
source /opt/ros/jazzy/setup.bash
source /turtlebot_ws/install/setup.bash
source /overlay_ws/install/setup.bash

The shell is now inside the simulation container. Run these commands individually:

printenv ROS_DISTRO
ros2 --help
ros2 pkg prefix tb_worlds
ros2 node list
ros2 topic list
ros2 topic info /scan --verbose
ros2 topic echo /clock --once
ros2 topic echo /odom --once --qos-reliability best_effort
ros2 topic hz /scan

Repeat the clock echo to verify advancing simulation time. Let the frequency command run for several seconds, then stop it with Ctrl+C. Expected topics include /clock, /odom, /scan, /tf, /tf_static, /map, and /cmd_vel.

If a sensor echo waits indefinitely, try a best-effort subscriber:

ros2 topic echo /scan --once --qos-reliability best_effort

The checkpoint is working CLI commands, advancing simulated time, and arriving sensor data. A particular scan frequency is not specified by the assignment.

15. Correct RViz localization if needed

Where: RViz2.

Use map as the fixed frame, /map as the Map topic, and /scan as the LaserScan topic. Adjust the initial pose only if the robot or scan is visibly misaligned. Click 2D Pose Estimate at the robot's actual map location and drag in its heading direction. This sets a localization estimate; it does not teleport the Gazebo robot.

Prioritize the map, robot model, laser scan, and required transforms. Some optional displays may reference topics that this robot does not publish.

16. Optionally verify navigation

Where: container shell and RViz2.

ros2 action list

Look for /navigate_to_pose. In RViz2, use Nav2 Goal or its equivalent to choose a nearby open-space goal and final heading. Expect a planned path, movement in Gazebo, and updated robot position in RViz2. Begin with a goal in the same room, away from walls. Check playback and localization if movement fails. This demonstration is optional verification.

17. Capture submission evidence

Capture readable screenshots of:
- The Jazzy environment, working ROS CLI, and installed tb_worlds package.
- ROS node and topic lists.
- Live sensor data and advancing simulation time.
- Gazebo showing the maze and TurtleBot.
- RViz2 showing the map, robot, and scan.
- Optional navigation evidence.

Increase terminal font size and keep commands and outputs visible together. Frame Gazebo and RViz2 so the required content is recognizable. Capture the actual run and inspect the saved images before submitting. Laptop screenshots of the DCV browser are already local.

Use captions supported by the results, such as "Gazebo displaying the TurtleBot3 in the course maze." Follow the course submission format. The assignment page does not specify an exact CLI screenshot count or a report template.

18. Check performance and troubleshoot

Where: EC2 host terminal.

nvidia-smi
docker stats
top

Keep only demo-world running, use the original maze, keep resolution near 1920x1080, and avoid builds while capturing evidence. Disable unnecessary RViz point-cloud or camera displays if the interface becomes slow. Gazebo's real-time factor compares simulated time with elapsed time; approximately 1.0 means real-time simulation. It is a diagnostic, not a grading threshold.

For simulation logs:

cd ~/robotics/turtlebot-maze
docker compose logs --tail=150 demo-world

Check the failing layer. DCV connection problems require checking the tunnel and sudo systemctl status dcvserver. Black desktops require checking sudo journalctl -u gdm3 -b --no-pager and the Xorg/NVIDIA configuration. Container GPU failures require checking the toolkit and Docker restart. Display failures require checking DISPLAY, XAUTHORITY, and xhost. Missing ROS commands require entering the container and sourcing setup files. Missing messages require checking playback, bridges, and QoS. Misalignment requires checking the fixed frame and initial pose. Fix the earliest relevant error.

19. Stop and resume safely

Exit the container shell:

exit

From the EC2 host project folder:

docker compose stop demo-world
xhost -SI:localuser:root

Save screenshots and notes locally, then stop EC2 through AWS. EBS storage charges continue, and instance-store data should not be treated as a persistent backup.

To resume, start EC2, check its current public IP, reconnect the SSH tunnel, check or recreate the DCV session, and log into the desktop. Open a desktop terminal:

cd ~/robotics/turtlebot-maze
xhost +SI:localuser:root
docker compose up demo-world

Recheck the display authentication path after a new desktop session. Unchanged images ordinarily do not need rebuilding.
