#The purpose of this Document:
- This document notes all the challenges/bugs/errors I faced for each task.
- It notes: Brief context (what was happening, what did I do? and in which scenario?), description (why it was happening), and how I fixed it
- lessons learnt during solving the task

Part 1: Setup challenges



1. Gazebo and RViz2 failed to open

Context: I launched demo-world from an SSH terminal on EC2.
Error: The graphical applications failed to open because they could not access the desktop display.
Cause: The SSH shell did not carry the active DCV desktop's display environment, and the container needed X11 access and authorization.
How I fixed it: I launched the service from a terminal inside the DCV desktop, checked DISPLAY and XAUTHORITY, verified the authentication file, and granted access with xhost +SI:localuser:root.
Lesson learnt: I learned that graphical containers needed access to the desktop session in addition to the application dependencies.

2. The Docker container could not access the GPU

Context: The host recognized the T4 through nvidia-smi, but the container GPU check failed.
Error: Docker could not provide GPU access to the container.
Cause: The NVIDIA container runtime needed configuration, and the simulation service did not explicitly request a GPU. Setting NVIDIA environment variables alone was insufficient.
How I fixed it: I configured the NVIDIA Container Toolkit for Docker, restarted Docker, and added the GPU reservation to the Compose override. I used docker run --rm --gpus all ubuntu:24.04 nvidia-smi to check container access.
Lesson learnt: I learned that host GPU access and container GPU access required separate configuration.

3. The simulation used software rendering

Context: Gazebo and RViz2 opened, but their updates were slow even though the T4 was available.
Error: The OpenGL renderer used llvmpipe instead of NVIDIA, so rendering ran on the CPU.
Cause: GPU compute access was available, but the container's graphics configuration did not select the NVIDIA rendering path.
How I fixed it: I compared glxinfo -B on the desktop and inside demo-world, enabled the NVIDIA graphics capabilities and GLX vendor setting in the override, and recreated the service. I checked the renderer again inside the container.
Lesson learnt: I learned that successful nvidia-smi output did not establish hardware-accelerated OpenGL rendering.

4. Docker reported a socket permission error

Context: I ran Docker commands after installation.
Error: Docker reported permission denied while connecting to its socket.
Cause: My current login session had not acquired docker group membership.
How I fixed it: I checked id -nG, added my account to the docker group, and fully logged out and back in. I then checked access with docker run --rm hello-world.
Lesson learnt: I learned that opening another terminal in the same desktop session did not necessarily apply new group membership.

5. ROS commands and project packages were not found

Context: I tried running ROS commands on the host and then in a fresh container shell.
Error: The host could not find ros2, and the container shell did not initially locate the project workspace.
Cause: ROS was installed inside Docker, and the new shell needed the ROS and workspace environments to be sourced.
How I fixed it: I entered demo-world and sourced /opt/ros/jazzy/setup.bash, /turtlebot_ws/install/setup.bash, and /overlay_ws/install/setup.bash. I checked the environment using ros2 --help and ros2 pkg prefix tb_worlds.
Lesson learnt: I learned to distinguish the host from the ROS container and to load the installed workspace before inspecting its packages.

6. The laser topic did not deliver messages to the CLI

Context: I inspected /scan while the maze simulation was running.
Error: The topic appeared in ros2 topic list, but the echo command waited without displaying messages.
Cause: The subscriber's reliability requirement was incompatible with the sensor publisher's best-effort QoS.
How I fixed it: I checked that /clock was advancing and inspected the publisher using ros2 topic info /scan --verbose. I then used ros2 topic echo /scan --once --qos-reliability best_effort.
Lesson learnt: I learned that topic discovery did not guarantee message delivery; the publisher and subscriber also needed compatible QoS.

7. The robot and laser scan were misaligned in RViz2

Context: The robot appeared correctly in Gazebo, but the laser points did not line up with the maze walls in RViz2.
Error: RViz2 displayed an incorrect estimated robot position relative to the map.
Cause: The localization estimate did not match the robot's actual starting pose.
How I fixed it: I checked the map fixed frame, the /map and /scan display topics, and the required transforms. I then used 2D Pose Estimate at the robot's actual map position and heading.
Lesson learnt: I learned that the localization estimate and simulated physical pose were separate, and that setting the estimate did not teleport the robot.

8. The DCV connection stopped working after restarting EC2

Context: I tried reopening the remote desktop after stopping and starting the instance.
Error: The desktop connection failed through the previous SSH tunnel.
Cause: The tunnel had closed, and the instance's public IP had changed.
How I fixed it: I checked the current public IP in AWS, re-established the SSH tunnel, and checked dcvserver and the available session before reconnecting through the browser.
Lesson learnt: I learned to recheck the instance address and tunnel after an EC2 restart instead of reusing the previous connection details.

Part 2: Object detection and event-storage challenges

1. Compose stopped because the database password was missing

Context: I started the Part 2 services from a new terminal on EC2.
Error: Compose reported that EVENT_DB_PASSWORD was required and did not start the stack.
Cause: The password had been exported in another shell and was absent from the current terminal environment.
How I fixed it: I entered and exported EVENT_DB_PASSWORD in the same terminal, checked the configuration with docker compose -f compose.events.yaml config --quiet, and restarted the services.
Lesson learnt: I learned that exported environment variables belonged to the current shell and were not automatically available in a new terminal.

2. PostgreSQL rejected the ingest worker's password

Context: I restarted the stack using an existing PostgreSQL volume after entering a different password.
Error: The ingest worker logged a password-authentication failure and did not store events.
Cause: The existing database retained its original password. Changing POSTGRES_PASSWORD in the container environment did not update the database account in the persistent volume.
How I fixed it: I restored the original password in EVENT_DB_PASSWORD and recreated the ingest service with the corrected connection settings. I retained the database volume and replayed the saved events after restoring access.
Lesson learnt: I learned that database initialization settings applied to a fresh volume, while an existing volume preserved its account credentials and records.

3. The detector dropped images without aligned odometry

Context: I started detection before checking that the simulation clock and odometry stream were advancing.
Error: The detector logged “Dropping image without timestamp-aligned odometry” and produced no stored frame events for those images.
Cause: The detector did not have odometry samples at, or closely bracketing, the image timestamp. Seeing the topic name alone did not establish that usable state data was arriving.
How I fixed it: I checked /clock and /odom inside the world container, resumed the paused simulation, and waited for live odometry before restarting detection. I checked that the world and detector used the same ROS_DOMAIN_ID.
Lesson learnt: I learned that detection events needed synchronized sensor and state data; substituting the latest available pose would have hidden the timing error.

4. Events contained an unavailable camera transform

Context: I inspected stored events after camera images and odometry started arriving.
Error: The events contained tf_ok=false and a null t_base_camera matrix.
Cause: The image's camera frame was not connected to the configured base frame in the available TF tree at the image timestamp.
How I fixed it: I checked the image header frame, the configured base frame, and the robot's TF publishers. I retained tf_ok=false and the null matrix for frames without a valid transform rather than replacing the camera frame with an unrelated frame or inserting an identity matrix.
Lesson learnt: I learned that receiving camera images did not establish a valid base-to-camera transform, and that unavailable transform data needed to remain explicit.

5. Stored frame counts were lower than the saved event count

Context: I compared the detector's local event spool with the database report after interrupting the messaging services.
Error: The report contained fewer frames than the detector had saved locally.
Cause: Live publications during the interruption did not reach the ingest worker. The detector's local spool preserved the original events, but publication alone did not confirm database storage.
How I fixed it: I restored the router and ingest services, replayed the run's metadata file and event spool, and regenerated the report. I replayed the same spool again to check that identical events did not increase the stored counts.
Lesson learnt: I learned that durable local records and idempotent replay were necessary for recovering observations after messaging interruptions.

6. Visible bench objects produced few detections

Context: I approached the benches while inspecting the robot's camera view and detector output.
Error: Objects visible in Gazebo produced empty detection lists or weak class predictions in the camera stream.
Cause: The objects occupied few pixels in the 320 × 240 image, and the procedural geometry differed from the photographic objects used to train the pretrained detector.
How I fixed it: I moved closer through clear space, faced the camera toward the bench, and inspected the actual camera view before changing detection settings. I treated weak recognition of the procedural models as an asset-quality limitation rather than a database or Zenoh failure.
Lesson learnt: I learned that choosing a COCO class name for an asset did not make its rendered appearance recognizable to a pretrained model.

7. Inference slowed the perception pipeline

Context: I ran Gazebo, RViz2 and YOLO together on the EC2 T4.
Error: Detection updates lagged while the simulation and visualization competed for resources.
Cause: Rendering and model inference shared the GPU, and processing more camera frames increased the workload.
How I fixed it: I kept the lightweight YOLOv8n model, reduced the detector's maximum processing rate, and disabled unnecessary RViz displays. I checked GPU utilization and simulation responsiveness before raising the processing rate again.
Lesson learnt: I learned that a higher inference rate did not automatically produce a better robotics pipeline when it reduced simulation responsiveness.
