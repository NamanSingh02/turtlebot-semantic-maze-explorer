#The purpose of this Document:
- This document notes all the challenges/bugs/errors I faced for each task.
- It notes: Brief context (what was happening, what did I do? and in which scenario?), description (why it was happening), and how I fixed it
- lessons learnt during solving the task

Part 1: Setup challenges



1. Gazebo and RViz2 failed to open

Context: I launched demo-world from an SSH terminal on EC2.
Error: The graphical applications failed to open because they could not access the desktop display.
Cause: The SSH shell did not carry the active DCV desktop's display environment, and the container needed X11 access and authorization.
How I fixed it: I launched the service from a terminal inside the DCV desktop, checked DISPLAY and XAUTHORITY, verified the authentication file, and granted access with xhost +SI:localuser:root.
Lesson learnt: I learned that graphical containers needed access to the desktop session in addition to the application dependencies.

2. The Docker container could not access the GPU

Context: The host recognized the T4 through nvidia-smi, but the container GPU check failed.
Error: Docker could not provide GPU access to the container.
Cause: The NVIDIA container runtime needed configuration, and the simulation service did not explicitly request a GPU. Setting NVIDIA environment variables alone was insufficient.
How I fixed it: I configured the NVIDIA Container Toolkit for Docker, restarted Docker, and added the GPU reservation to the Compose override. I used docker run --rm --gpus all ubuntu:24.04 nvidia-smi to check container access.
Lesson learnt: I learned that host GPU access and container GPU access required separate configuration.

3. The simulation used software rendering

Context: Gazebo and RViz2 opened, but their updates were slow even though the T4 was available.
Error: The OpenGL renderer used llvmpipe instead of NVIDIA, so rendering ran on the CPU.
Cause: GPU compute access was available, but the container's graphics configuration did not select the NVIDIA rendering path.
How I fixed it: I compared glxinfo -B on the desktop and inside demo-world, enabled the NVIDIA graphics capabilities and GLX vendor setting in the override, and recreated the service. I checked the renderer again inside the container.
Lesson learnt: I learned that successful nvidia-smi output did not establish hardware-accelerated OpenGL rendering.

4. Docker reported a socket permission error

Context: I ran Docker commands after installation.
Error: Docker reported permission denied while connecting to its socket.
Cause: My current login session had not acquired docker group membership.
How I fixed it: I checked id -nG, added my account to the docker group, and fully logged out and back in. I then checked access with docker run --rm hello-world.
Lesson learnt: I learned that opening another terminal in the same desktop session did not necessarily apply new group membership.

5. ROS commands and project packages were not found

Context: I tried running ROS commands on the host and then in a fresh container shell.
Error: The host could not find ros2, and the container shell did not initially locate the project workspace.
Cause: ROS was installed inside Docker, and the new shell needed the ROS and workspace environments to be sourced.
How I fixed it: I entered demo-world and sourced /opt/ros/jazzy/setup.bash, /turtlebot_ws/install/setup.bash, and /overlay_ws/install/setup.bash. I checked the environment using ros2 --help and ros2 pkg prefix tb_worlds.
Lesson learnt: I learned to distinguish the host from the ROS container and to load the installed workspace before inspecting its packages.

6. The laser topic did not deliver messages to the CLI

Context: I inspected /scan while the maze simulation was running.
Error: The topic appeared in ros2 topic list, but the echo command waited without displaying messages.
Cause: The subscriber's reliability requirement was incompatible with the sensor publisher's best-effort QoS.
How I fixed it: I checked that /clock was advancing and inspected the publisher using ros2 topic info /scan --verbose. I then used ros2 topic echo /scan --once --qos-reliability best_effort.
Lesson learnt: I learned that topic discovery did not guarantee message delivery; the publisher and subscriber also needed compatible QoS.

7. The robot and laser scan were misaligned in RViz2

Context: The robot appeared correctly in Gazebo, but the laser points did not line up with the maze walls in RViz2.
Error: RViz2 displayed an incorrect estimated robot position relative to the map.
Cause: The localization estimate did not match the robot's actual starting pose.
How I fixed it: I checked the map fixed frame, the /map and /scan display topics, and the required transforms. I then used 2D Pose Estimate at the robot's actual map position and heading.
Lesson learnt: I learned that the localization estimate and simulated physical pose were separate, and that setting the estimate did not teleport the robot.

8. The DCV connection stopped working after restarting EC2

Context: I tried reopening the remote desktop after stopping and starting the instance.
Error: The desktop connection failed through the previous SSH tunnel.
Cause: The tunnel had closed, and the instance's public IP had changed.
How I fixed it: I checked the current public IP in AWS, re-established the SSH tunnel, and checked dcvserver and the available session before reconnecting through the browser.
Lesson learnt: I learned to recheck the instance address and tunnel after an EC2 restart instead of reusing the previous connection details.

Part 2: Implementation challenges

1. The local Docker daemon was unavailable

Context: I tried to use Docker while preparing database and runtime verification.
Error: Docker could not connect to its Unix socket because the daemon was not running. Starting the application did not produce an available daemon during the checks.
Cause: The local Docker runtime was unavailable, independently of the Compose configuration.
How I fixed it: I installed PostgreSQL locally and started a separate temporary database for transaction tests. I validated Compose without the daemon. I did not complete a Docker image build or a ROS simulation run.
Lesson learnt: I learned that checking configuration and testing database behavior could proceed independently of the container runtime, but neither established that the complete simulation worked.
